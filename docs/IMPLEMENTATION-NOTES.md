## 1. 本次改了什么

| # | 问题 | 涉及文件 | 修法 |
|---|---|---|---|
| 1 | **两位数解析缺陷**：`y = (cellStr.length >> 1) + 1` 假定每个元素只占一位，第 2 行出现 `10,11,12` 时列数算错，二次展开越界 | `core/matrix.ts` `txma()` | 按实际元素个数 `cellStr.split(',').length` 推断。覆盖全部 `ymode=0` 记号 |
| 2 | **零表达式 `"0"` 在 8 个 `bias=1` 序列记号里被误判为后继**（`typeOf` 返回 `2`） | `core/seq.ts` `txar()` | `"0"` 直接返回全 0 数组，不解析成单元素 `[bias]` |
| 3 | **`fsLimit(0)` 越界**：返回的是后继表达式，不在极限基本列里；序数尺根节点因此不是极限序数（修正前 31 个记号、当时含 `pps4_v2`，有 21 个） | `core/seq.ts` 三个 `seqLimit*`、`core/notation.ts` `limitMat()`、`lprss` / `kp_hydra` / `pss_hydra` / `stos` / `ppm00t` / `remainder_retention` | 统一 0-based：`fsLimit(a)` = 极限基本列第 `a` 项。集成测试里「根节点非极限」从 21 个降到 1 个（LELS，见 §3） |
| 4 | **零 / 后继表达式调用 `fs` 产出语法垃圾**：KP Hydra `"()" → ")"`、PSS Hydra 不平衡串、RCS `"0" → "-1"`、BMS 无坏根矩阵被强行复制 | `core/notation.ts` 两个基类 `fs()`，及 5 个自定义 `fs()` | `typeOf(s) !== '3'` 时短路。零返回 `"0"`，其余返回**原表达式** |
| 5 | **`pred` 违反 ONP2 协议**：空矩阵 / `"0"` 返回 `""` 而非 `"0"` | `core/matrix.ts`、`lprss` / `kp_hydra` / `pss_hydra` | 空矩阵、单列矩阵、零表达式一律返回 `"0"` |
| 6 | **CpS 死循环**：`fb[0] = 0` 且无输入校验，非标准输入 `0,2,4` / `2,4,8` 的 `fs` 永不返回，宿主挂死 | `coprime.ts` | `hasCommonFactor` 换标准 `gcd`（`gcd(0,b)=|b|` 语义正确）；父链加自环护栏 |
| 7 | **LELS 死循环**：`(0)` / `(0)(0)` / `""` / `"abc"` 的 `fs(1)` 越界读恒 0，无限递增列下标 | `lels.ts` | 只加列上界护栏与 `typeOf` 分流，**展开算法未动**（见 §3） |
| 8 | **0-Y 栈溢出**：`1,-1` 一类非法串让 `exRec` 递归不收敛 | `zero_y.ts` | 递归深度上限 64，超出按「落差为 1」分支照抄 |
| 9 | `bias=1` 的 `9 / 99 / 999` 解析步进错位 | `core/seq.ts` `txar()` | 已由上游 commit `72d5154` 修正为 `log10((v + (v==0)) * 100 + 1)`，本次沿用 |

回归测试见 `tests/verify_notations.mjs`（`npm run verify:notations`）。

### 关于第 4 项为什么返回「原表达式」而不是 `"0"`

ONP2 协议写「结果为 0 时一律返回 `"0"`」，但宿主 `EngineHost.firstExceeding()`
用谓词 `P(i) = a < FS(base)[i]` 做指数搜索 + 二分，要求 `P` 对 `i` 单调。
若零/后继的 `fs` 一律返回 `"0"`，`P(i)` 会恒假，序数尺在初始化时抛
「基本列扫描超过 1000000 项」并整页失效。返回原串则 `less(s, s) = false`，
谓词保持单调且不会误判。这是**宿主契约决定的工程取舍**，不是定义要求。

## 2. 明确不改的部分，以及基准口径

审查报告里标 ❌ 的「基本列第 n 项」偏差，绝大多数属于**基准选择**而非 bug。
以下各项本轮**一律保留**，请按此口径使用插件。

### 2.1 `fs(n)` 的块数偏移（5 个记号）

| 记号 | 实现 `fs(n)` | Wiki / 定义 |
|---|---|---|
| `zero_y` | 定义第 `n` 项再**多 `l-1` 项**（`l` = 坏部项数） | 第 `q` 项 |
| `bashicu_matrix`（含 4 个 BMS 变体） | `n+1` 个 B 块 | `n` 个 B 块（BM4 形式定义与实现一致） |
| `lprss` | `S[n+1]` | `S[n]` |
| `kp_hydra` | `S[n+1]` | `S[n]`（砍树游戏 step n 复制 n 份） |
| `pss_hydra` | `P[n+1]` | `P[n]` |

**不改的理由（硬约束）**：`EngineHost.validate()` 从 `Limit` 出发，靠
「反复取基本列项 / 前继」向下逼近目标串；`validate` 的结果又被杂项页和缓存依赖。
把块数改成 `n` 后，`fs(0, s)` 不再是「删末项」，逼近链不再闭合：
实测 `pss_hydra` 的 `firstExceeding` 扫描满 100 万项仍不收敛、`zero_y` 出现
基本列非单调，序数尺 / 展开树直接抛错。这类改动会与原有功能组合出问题，故保留。

**`PPS` 家族不同**：`ppsEx` 的哨兵落在 `nL+x-1`、PPM 的 `this.x = nL+x-1`，
`fs(n)` 本来就等于定义的基本列第 `n` 项，没有这一格偏移。报告里「全库统一偏移」
的说法应收窄到上表 5 个记号。

### 2.2 PPS 家族三处实质偏差

按定义独立实现做差分，`pps2` 有 197/1200、`pps4` 有 554/1200 次不一致，
可归到：复制阶段多了「提升点」例外、PPS1 在 `b=x` 边界漏掉强展开的 `-1`、
PPS4 在找不到可回落项时缺少「等同弱展开」兜底。

**保留理由**：`ppsEx` 是 7 个记号（`pps2` / `pps3` / `pps4` / 4 个弱化版）
共用的骨架，`prss_parented` 也走它；改动会整体改变展开输出。而 Wiki 页面给出的
4 个长表达式（含「地府第一层」「良序极限基本列」）在 `pps2` 上 `n=0..3`
**逐项完全一致**，说明现值在真实用例上成立。此外当前的 `pps4` 已替换为与用户提供的 exe 逐条对拍过的那个版本
（见 `docs/pps4-v2.md`），不宜按 Wiki 定义重写。

### 2.3 LELS

定义晦涩（鉴定元、提升度、`δ[n]`、序数减法等形式化条款缺失），且现有实现是
**按原作者提供的 C++ 源码逐行复原**并已据其更正过 `less` 的不反对称问题。
本轮只修死循环与协议短路（§1 第 5、7 项），**不按定义改写差值表 / 坏根 / 分支**。
报告的三处可定量偏差（差值表左侧抄原值、`isUnit` 绕过坏根、`typeOf` 与 `ex` 分支矛盾）
按原样保留。

### 2.4 RCS / RRSS

- **RCS fallback**（祖先链上无覆盖全部余数类者，490/1050 样本走此支）：定义只给了
  坏根为第 0 项 `s`，`[0,-k)` 区间记号与「x 右边的项」读法均不闭合，且**未给展开规则**。
  保留 exe 实测分支，不做定义外推。
- **RRSS**：坏根应取阶商序列末项的直接父、坏部应含坏根，源码沿父链上溯且从
  `base+1` 起复制；Wiki 的 5 段无穷降链未复现。词条未给出 `[n]` 复制次数公式，
  无法写出无歧义的独立参考展开器，保留 exe 实测行为。
- **RRSS 的空格分隔**（`1 4 5 4`，Wiki 用逗号）是 exe 私有串格式，改动会让所有
  既有表达式失效，保留。

### 2.5 其他约定

- `less` 一律是**字典序**（矩阵类按行字典序 + 行数），不是各记号的序数序；
  这是实现约定，定义未覆盖。实测序性质（反自反 / 非对称 / 完全 / 传递）全 0 违反。
- `ppm.ts` 自报 `name` 为 `Parented Predecessor Matrix 2`，实现的是 **PPM 1.2** 的
  弱/强判定；PPM 2 独有的字典序判定与 `i > y-L+1` 未实现。exe 的 `name0()` 也打印
  PPM 2，故保留名字不改，仅在此登记版本归属（`ppm3` 对应 PPM 3，`ppm00t` 在 Wiki 无定义）。
- **PPS4 已于 2026-11-08 替换**：与用户 exe 不符的旧复原版已删除，
  11/7 那份实现从 `pps4_v2` 提升为唯一的 `pps4`（`name` 无后缀，注册表 31 → 30）。
  两版差异只在 `Ex()` 的降级扫描下界，详见 `docs/pps4-v2.md` 与
  `docs/pps4-v2-changes/`。
- 非法表达式（不校验定义域、括号匹配、等级约束）仍被静默接受，但 §1 的短路与护栏
  保证不会产出负数 / 不平衡括号串 / 死循环。

## 3. 集成验证结果与已知限制

在 30 个记号上跑 `tests/integration.mjs`（宿主 + 序数尺 + 展开树 + validate）、
`tests/verify.ts`、`tests/check_names.mjs`，以及逐记号压力脚本：

- **初始化失败 0 个**；`npm run verify` 全部通过；名字表 30 个一致。
- 序数尺：`firstExceeding('0','Limit')` 在 30 个记号上全部返回合法的**极限表达式**；
  连续拉近 60 次 / 拉远 120 次 / 反复横跳 40 轮、密集刻度绘制均不崩溃。
- 展开树：初始化、点击展开、连续展开、滚动均正常。
- `validate` 对 `fsLimit(0..3)` 产出的串全部判合法。
- **原版 vs 修正版同脚本压力对比**（连续点击展开树 12 次 + 缩放 130 轮 +
  密集刻度 + `validate` 抽样）：原版在 9 个记号上抛
  `Cannot read properties of undefined (reading 'adj')`，修正版**全部消除**；
  两版各自有 7 个记号在 8 秒超时内跑不完 `validate` 逼近链，名单完全一致，
  **没有引入新的组合失败**。改善来自 `fsLimit(0)` 现在是合法的极限表达式，
  展开树的初始节点与点击路径不再落到边界外。

**已知限制（原版固有，本次未引入）**：`validate` 对多列矩阵的前驱串
（如 `bashicu_matrix` 的 `(0,0)`）判为非法。逼近链上的极限基本列是
`(0)(1)` / `(0,0)(1,1)` / …，单行两列全零矩阵不在链上，因此撞不上。
`fsLimit` 改 0-based 后这个盲点会提前一轮出现（`fs(0, fsLimit(1))` 起），
但性质与原版 `fs(0, fsLimit(2))` 的失败完全相同，不影响序数尺与展开树。

npm install

PSS Hydra 三实例、CpS 1050 次、RCS 560 次、PPS Wiki 四长表达式）
